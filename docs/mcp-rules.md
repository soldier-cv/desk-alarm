# agent 该守的规矩

MCP 给的是能力面，判断还得靠技能。这一份是「这个用户的习惯」层面的约定，不是工具文档。

## 开工前

**先 `today_digest`，不要凭印象动手。** 这个用户可能一早就把提醒挪过了，也可能昨晚在另一台设备上完成了几条。凭上下文里的记忆去改，会把已经处理过的事又翻出来。

## 建条目前想清楚这三种情况

| 用户说的话 | 该建什么 | 常见的错 |
|---|---|---|
| 「别老忘这个链接」 | 收集箱，不定时间 | 自己加个「15 分钟后提醒」 |
| 「三点提醒我交周报」 | 定时，**默认弱提示** | 直接建强提示 |
| 「一定要提醒我吃药」 | 定时，强提示，reason 填用户原话 | 强提示但不给 reason |

第一条是最容易犯的错。用户说「别老忘」的时候，意思是「记下来别让我现在分心」，不是「打断我」。真要什么时候提醒他得反问一句。

第三条只有在他用了「一定要」「必须」「别忘」这类词时才成立，而且 reason 要写他的原话，不是你的转述。

## 改东西之前

**批量改期要先列再问。** 「今天要干的都往后推半小时」听起来是明确的，但里面藏着已逾期的条目，那些已经晚了半小时，再推半小时用户不一定想要。分两批问：

```
要推迟的是这 3 条：……
另外有 2 条已经逾期 1 小时以上了，还要一起推吗？
```

**不要重新打开已完成的事。** 用户说「昨天那个邮件我回了」是在告诉你信息，不是在要你改状态。

**删除是不可逆的。** 哪怕是被忽略 4 次的条目，也得让用户自己点删除，或者明确说「删掉吧」。

## 关于强度

强弱提示的默认是 weak，这不是保守，是**提醒疲劳是提醒类工具死掉的头号原因**。全都在喊，结果是全都听不见。

所以：

- 不要主动把 weak 升级成 strong
- 不要因为「怕用户错过」就建强提示。**用户漏掉一条弱提示的代价，远小于他被一次全屏打断的代价**
- `today_digest` 里的「被反复忽略」是让你提醒用户去调整，不是让你替他决定

## 一次只做一件事

用户发来一句话，只回应对应的那一条。不要「顺便」把他上周提过的其它事一起处理掉。要做别的，列出来问。

## 汇报方式

做完之后说人话：

```
建好了：「交周报」明天 15:00 提醒你，弱提示。
```

不是：

```
create_entry 返回 201，entry_id=e_xxx，remind_at=1790580000000，strength=weak
```

如果要改一批，先给 diff 再问，不要直接改完再汇报。
