# agent 该守的规矩

MCP 给的是能力面，判断还得靠技能。这一份是「这个用户的习惯」层面的约定，不是工具文档。

## 开工前

**先 `today_digest`，不要凭印象动手。** 这个用户可能一早就把事项挪过了，也可能昨晚在另一台设备上完成或归档了几条。凭上下文里的记忆去改，会把已经处理过的事又翻出来。`today_digest` 里还有今天剩余几次强打扰额度，别把配额浪费在 agent 自己推断的「重要」上。

## 建事项前想清楚这三种情况

| 用户说的话 | 该建什么 | 常见的错 |
|---|---|---|
| 「别老忘这个链接」 | 收件箱，不定时间 | 自己加个「15 分钟后提醒」 |
| 「三点提醒我交周报」 | 推进项，`dueAt` 写三点 | 自己把 importance 改成 P0 |
| 「一定要提醒我吃药」 | 推进项，`importance=3`，reason 填用户原话 | P0 但不给 reason |

第一条是最容易犯的错。用户说「别老忘」的时候，意思是「记下来别让我现在分心」，不是「打断我」。真要什么时候提醒他得反问一句。第三条只有在他明确用了「一定要」「必须」这类词时才成立，而且 reason 要写他的原话，不是你的转述。

## 状态是有边界的

- **进行中 / 收件箱 / 暂停**：完成、延期、拆小、归档都能做。
- **已完成**：只能撤回（`reopen`）或归档。用户说「昨天那个邮件我回了」是在告诉你信息，不是在要你撤回——别重新打开。
- **已归档**：没有任何跟进动作。拿不准要不要动它，先 `clone_pursuit` 一份再决定。
- **任何状态都能克隆**：复制内容和步骤文本，步骤状态重置、截止清空、不复制跟进历史。克隆不是跟进动作，不会停铃，也不占配额。

批量改期要先列再问。「今天要干的都往后推半小时」听起来明确，但里面藏着已逾期的事项，分两批问：

```
要延期的是这 3 条：……
另外有 2 条已经逾期 1 小时以上了，还要一起推吗？
```

## 关于重要性

重要性只有 P0 / P1 / P2，默认 P2。截止落在 24 小时内时，客户端展示和服务端排期会自动按 P0 算，但**用户存的值不变**——不要看到界面显示 P0 就以为用户把配置改了。

不要主动把 P2 提到 P0。用户漏掉一条普通优先级的事项，代价远小于被全屏接管打断一次。打扰强度由引擎按等级和每日配额决定，没有「强/弱提示」开关可拨。

## version 和两步写

写之前先 `get_pursuit` 拿最新 `version`；`plan_changes` 只给预览，`apply_changes` 才落库，plan_id 一次有效、十分钟过期。不要因为 plan 失败就立刻重试第二次——先重新 `get_pursuit`，确认是不是别人刚改过。

## 一次只做一件事

用户发来一句话，只回应对应的那一条。不要「顺便」把他上周提过的其它事一起处理掉。要做别的，列出来问。

## 汇报方式

做完之后说人话：

```
建好了：「交周报」明天 15:00 截止，P2。
```

不是：

```
create_pursuit 返回 201，id=p_xxx，importance=1，dueAt=1790580000000
```

如果要改一批，先给 `plan_changes` 的预览再问，不要直接改完再汇报。
