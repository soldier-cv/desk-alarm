# Agent Note: 恢复「到点响」并改为按状态停止的持续提醒

Status: implemented

## Problem

v2 把提醒模型从「到点响」换成「停滞阶梯」后，`dueAt` 只剩排序权重和文案里的「已逾期」含义，不再触发任何通知。用户写下「1 分钟后提醒」，到点那一刻什么都不发生；唯一能触发通知的是停滞满 2 小时（L2），且 fireKey 为 `${level}-${日期}`，同级一天只发一次。表现为「输入了时间但系统忽略」，比不支持时间更伤信任。同时客户端 L2 响 6 次、L3 响 3 次就停，靠计数器放弃跟进。

## Decision

到点通知与停滞阶梯分属两条路径，各自负责不同来源的信号：

- **到点通知（`server/src/drive.ts` 的 `driveUser`）**：`dueAt <= now` 时创建一条 L2 `notification` 类型的 nudge，fireKey 为 `due-${pursuitId}-${dueAt}`。绑定 `dueAt` 保证同一截止只响一次；「改天」改掉 `dueAt` 后会生成新 key 再响。不占 `dailyStrongBudget`——用户自己约的时间属于履约，不是系统强打扰。
- **静音让路**：静音时段整批跳过到点通知，不写 nudge；下一 tick（静音结束）自然补发。循环事项在静音期不推进 `dueAt`，否则原截止被改掉，补发就丢了。
- **合并补发**：同一 tick 多条到点时，按 `weightOf` 排序只推权重最高的一条，其余建 nudge 后立刻 `markAcked(id, 'coalesced')` 占位——既合并通知，又挡住后续 tick 重复触发。同一次到点已发通知的条目不再叠加同级的停滞通知。
- **持续提醒（`app/src/alarm.ts`）**：用 `REPEAT_LADDER` 做先密后疏的递增间隔（L2 为 1/3/10/30/60 分钟，之后保持 60 分钟），删掉 `MAX_ATTEMPTS` 计数上限。静音期只顺延、不消耗次数。停止条件只有用户明确动作（推进/改天/归档）、别的设备处理、或等级升级——没有「响够 N 次」这种按计数器的放弃。
- **不加「知道了，今天别提了」出口**：用户确认只有真正处理才算停止，避免用静默换安静。
- **通知文案**：标题用事项原文，正文用 reason 加次数，不再暴露 `L2`、`第 N 次` 之外的内部等级术语。
- **安卓原生保活服务（`DeskAlarmKeepAliveService.kt`）**：它原本还是 v1 协议，只认 `entry.fired/weak/acked` 和 `escalateAfterSec/repeatEverySec/maxRepeatCount`，而 v2 服务端一个都不发。锁屏后 WebView 的 JS 被冻结，原生服务维持着 WS（设备显示在线、nudge 被标记已投递）却不弹任何通知。现已切到 `pursuit.nudge`：按 level 决定 L1 静默、L2+ 强通知；重复阶梯与 `alarm.ts` 一致、无次数上限；`pursuit.followed/deleted` 才取消；静音沿用 `inQuiet()`；welcome 的 missed 合成一条汇总。本机无 Android SDK，Kotlin 改动未编译验证。

## Alternatives considered

- **提前量提醒（截止前 5～10 分钟响）**：放弃。需要猜测任务耗时，引入用户没要求的选择；准点更可预测，符合「写了什么时间就什么时间响」的契约。
- **保留 6 次上限**：放弃。用户明确要求不处理就持续提醒；6 次后闭嘴会让事项继续烂在列表里。
- **无限同频重复（固定每 5 分钟）**：放弃。虽然意图对，但固定高频会触发通知疲劳，用户会关掉整个通知通道，最终什么也提醒不到。递增间隔在不放弃跟进的前提下控制密度。
- **到点通知计入强打扰额度**：放弃。额度约束的是系统自作主张的打扰，用户自己约定的时间不属于这一类。
- **给「知道了」静默按钮**：放弃。用户选择只有显式处理才算停止。

## Consequences

收益：写下的时间重新变成有效输入；未处理的事项会持续跟进且不再按计数器放弃；静音期不打扰、结束后补发；多件事同时到点不会连轰。

代价：服务端每 tick 多一次过滤和幂等查询（已有 `due_at` 索引）；客户端静音期顺延的定时器在长时间静音里会持续重排；到点通知不占额度意味着强打扰总额度不再覆盖这类通知，需要靠递增间隔和静音规则控制密度。验证依赖 `TICK_MS`/`ROTATE_MS` 可调，冒烟测试用 200ms 加速跑。
